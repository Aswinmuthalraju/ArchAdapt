# Agent 2 — Independent Audit of Agent 3 Remediation

**Audit target:** `feature/agent-3-core-engine`, `4829c60daae02e94e640f8a516cce2a49e11ee28`  
**Audit scope:** repository code, history, tests, benchmark outputs and screenshots available in this checkout. No application code or tests were changed.

## 1. Executive verdict

**Verdict: meaningful engineering progress, but not yet a launchable AI residential architecture product.** Agent 3 adds a real deterministic spatial search, polygon-aware envelope checks, room-program interpretation, geometry-edit proposals and guest-side persistence. The verified comparisons show tangible improvements for the narrow, irregular and courtyard cases. The ordinary rectangular plan still selects the old band solver in the representative 40×60 and 80×120 cases. The What-If path is sometimes surgical and sometimes falls back to a whole-plan regeneration; the central reported 13-of-17 movement case could not be reproduced from the supplied test fixture, and the added browser test does not assert that a request changes only the named room. That core reliability question remains unresolved.

This implementation does not establish architect-reviewed planning quality, building-code compliance, construction readiness or reliable authenticated persistence. The engine is a conceptual layout generator with useful geometric validation, not a professional design approval system.

**Direct answer:** Agent 3 moved ArchAdapt closer through a substantive optimizer and review workflow, but fundamental generation and editing limitations remain. It is not yet credible to describe it as a launchable AI residential architecture product.

## 3. Actual implementation changes

The commit history adds a planner under `src/lib/design/planner/`, the quality scorer in `src/lib/design/quality.ts`, What-If geometry operations in `src/lib/design/surgery.ts`, brief parsing in `src/lib/genai/briefing.ts`, polygon support, admission control, new UI components and tests. `layoutEngine.ts` remains the original zoned-band solver and shared canonical geometry realization. `planner/index.ts` runs that solver and the optimizer as candidates, validates candidates, scores them and chooses the highest-ranked result; setting `ARCHADAPT_PLANNER=band` skips optimizer search.

The optimizer is a deterministic-seeded slicing-tree simulated annealer. Candidate room rectangles are generated by seeded tree construction, annealed/repaired, assembled through the existing geometry pipeline and filtered by validation. The energy model penalizes room size/shape, access/reachability, adjacency, privacy, daylight/exterior exposure, wet-room and structural relationships, orientation and other terms. Some terms are intended as hard conditions (`HARD_TERMS`); the final candidate still depends on repair and validation, rather than a formal proof of global constraint satisfaction. It searches a single rectangular building footprint per floor inside a polygon-derived buildable envelope; it does not synthesize arbitrary multi-wing or L-shaped building footprints.

The selector includes the band result, when valid, and often keeps it. This is a hybrid deployment path, not a replacement of the old solver for the ordinary user case.

## 5. Optimizer architecture assessment

The implementation is a genuine algorithmic addition, not a renamed band heuristic: simulated annealing explores slicing-tree room arrangements under a weighted energy function, and candidates are evaluated by a shared quality scorer. It supports standard rectangular plots and polygonal outlines through an envelope rasterization/placement process, with orientation and per-edge setback inputs. It handles the repository's listed trapezoid, cut-corner and L-shaped plot cases as rectangular floor footprints placed within the polygon envelope.

Constraints in `energy.ts` are a mixture of penalty terms and designated hard terms. Final validation catches geometric envelope, overlap, opening and reachability failures, while the optimizer has hard-cost/repair passes for some planning conditions. The score remains a hand-authored proxy: it does not simulate code compliance, structural engineering, daylight levels, ventilation performance, occupant ergonomics or buildability. `quality.ts` gives a 0–100 score that should not be presented as an objective professional quality rating without independent calibration.

The default seed is derived from site/program/archetype, making same-input searches deterministic unless a seed offset/attempt changes it. The measured `compare.ts` run took about 1.4–7.5 seconds per optimized case; one 40×60 case took 2.7 seconds, L-shaped took 7.5 seconds. This is materially slower than the 1–25 ms band path and can block a Node event loop during synchronous search. No true worst-case bound or stress test was performed.

## 7. What-If surgical editing assessment

`runWhatIf` parses a delta, applies it to a copied program, calls `attemptSurgery`, then falls back to `realiseProgram` with position anchors if surgery fails. `surgery.ts` reconstructs rectangles from canonical room positions through `roomRectFt`; it does not require optimizer metadata to attempt operations. Wall pushes require a straight shared wall whose adjacent groups cover the same span; local resolution builds a slicing tree from existing rectangles and refuses moves that affect fixed stair/courtyard/attached-bath geometry. These geometric preconditions explain why some layouts and operations fall through to whole-plan realization.

Independent deterministic probe: `npx tsx tests/tools/whatif-probe.ts 40 60 3 2 "Make the kitchen 20% larger"` with provider keys removed produced a **Zoned bands** base (score 86.1) and a **wall-push** edit. The kitchen changed from approximately `10.532 × 9.348 ft` (reported as 98 sq ft) to `13.028 × 9.348 ft` (122 sq ft). The tool reported 16/17 existing rooms preserved; the kitchen is the only changed existing room. Thus in this fixture the kitchen enlargement succeeds surgically on the band plan.

That differs from Agent 3's report of a browser-generated 40×60 plan where the same request fell back to full replan and moved 13/17 rooms. The test fixture does not document enough exact onboarding state/program IDs to reproduce that plan, and the browser E2E test does not assert the edit strategy, dimensions, or changed-room count. I cannot reconcile the two results from repository evidence. **The product-level question—whether ordinary user-generated plans reliably preserve unrelated rooms—remains unresolved.** The implementation itself has deterministic failure cases and a whole-plan fallback, so a proposal card alone must not be treated as successful surgical behavior.

The code's fallback explicitly tells the user it replanned the whole house and lists touched rooms. That is better than silently pretending it preserved the design, but still permits a single-room request to move unrelated rooms. No reproducible acceptance test currently gates that behavior for both band-generated and optimizer-generated canonical designs.

## 8. AI contribution assessment

The AI integration is meaningfully separated from geometry. `buildProgramPrompt` asks Gemini for a structured room programme, room areas/floors/zones/relationships, intent priorities and rationale; `parseProgram` validates the response, then deterministic code lays out the rooms. The AI does not produce coordinates or directly control wall geometry. `briefing.ts` uses deterministic regex/rule extraction for household context and notes; an optional AI intent block is merged with the rule intent. The built-in fallback generates a deterministic template programme.

This is a hybrid AI-assisted planner, not a generative architectural geometry model. Gemini can influence room programming and relationships, while the optimizer handles spatial arrangements. In this local audit, no live output was captured as a clean controlled AI-vs-fallback A/B. Unit tests include mocked Gemini responses; `npm test` also attempted real calls with quota failures. The audit therefore verifies the integration shape, not the quality or consistency of actual model reasoning. Fallback is identified in code and UI metadata, which is a positive integrity measure.

## 9. Guest and authenticated persistence

The What-If route now accepts a browser-supplied design for guest/offline projects and validates accepted design data with `validateFloorPlan`. Guest project persistence is browser-local; the E2E test is designed to check accepted SVG survives reload. This audit did not execute that browser test, so guest reload persistence is **supported by implementation and reported test only, not independently reverified here**.

For authenticated projects, the server uses the caller's Supabase bearer token and anon key; schema policies scope project/version reads and writes through `auth.uid()`. No service-role key was found in the inspected server client path. The database is therefore intended to enforce ownership with RLS. This audit did not run an authenticated project against a live Supabase instance or test cross-user access, so authenticated persistence and RLS behavior are code-reviewed, not runtime-verified.

On accept, the route revalidates the submitted design before inserting a new `floor_plan_versions` row. The check verifies a valid design structure and geometric validator result, but it does not prove that the accepted design is a proposal previously issued for that project/version. Concurrent version writes also derive `nextVersionNumber` from a prior read; database uniqueness may reject one race, but no retry/transaction is evident in this route. Treat this as a P2 concurrency/data-integrity risk for simultaneous edits, not as an observed exploit.

## 11. Server performance and concurrency

`src/lib/design/admission.ts` maintains a module-local in-flight counter, defaults to six, reads `ARCHADAPT_MAX_CONCURRENT_PLANS`, releases in `finally`, and throws `BusyError`; all three design routes translate it to HTTP 503 with `Retry-After`. Unit tests verify over-limit rejection and release after success/failure. This limit is per process/instance, not shared across replicas or serverless workers. It cannot enforce a global quota.

The main performance issue remains: optimization is CPU-bound and synchronous, with observed searches up to about 7.5 seconds in this audit and report claims up to 8 seconds. A single long solve blocks unrelated event-loop work on that instance. An in-memory count is not a worker pool and may not prevent queued requests from waiting behind synchronous work. A worker queue/service is appropriate before multi-user production load; a distributed admission mechanism is needed if the intended cap is global. Memory and multi-instance stress behavior were not measured.

## 13. Security and data integrity

- The acceptance route validates a submitted design server-side before persistence. Authentication uses a bearer token and RLS-scoped anon client; the inspected path does not use service-role credentials.
- RLS policies in `supabase/schema.sql` bind projects and related versions to `auth.uid()` via project ownership. Storage ownership is tightened in migration `002_auth_hardening.sql`.
- Guest designs sent by the browser are untrusted input; structural checks (`isDesign`) plus `validateFloorPlan` reduce risk, but this is not schema validation for every nested field. No exploit was demonstrated in this read-only audit.
- Reject/accept behavior and data isolation were not run in a real browser/Supabase session here. No P0 security defect was found from static inspection; runtime authorization assurance remains incomplete.

## 14. Unresolved issues

1. **P1 — What-If is not proven reliably surgical on ordinary user plans.** The report describes a 13/17 movement full-replan, while the current reproducible 40×60 synthetic band fixture gets a wall-push edit. The browser test checks proposal mechanics, not preservation. Missing exact browser-generated fixture prevents reconciliation.
2. **P1 — Ordinary rectangular generation often remains the band solver.** It wins the tested 40×60 and 80×120 cases with no quality score improvement. The optimizer materially improves selected edge cases but is not a general quality upgrade on those ordinary briefs.
3. **P1 — Quality and suitability remain unreviewed.** The scorer is in-house and geometrical/function proxies do not establish architectural correctness, local regulatory compliance, structural safety or construction readiness. The report itself acknowledges no architect review.
4. **P1 — Optimizer blocks the event loop.** The six-request limit is per instance; it is not a worker pool or fleet-wide protection mechanism.
5. **P2 — Browser and production build claims not independently verified in this environment.** Build failed at `.next` creation due EPERM; therefore production browser E2E and guest persistence were not rerun.
6. **P2 — Authenticated persistence not tested against live Supabase.** RLS is present in schema and caller-token code, but no live cross-account/runtime test was executed.
7. **P2 — AI quality not independently evaluated.** The tests include mocks and local suite attempted live provider calls, but no controlled model/fallback comparison was recorded here.
8. **P2 — Test suite can depend on live API state.** Gemini quota/failover logs appeared during `npm test`; provider-dependent tests should remain isolated or fully stubbed for repeatability.
9. **P2 — Acceptance version numbering is not visibly transactional.** Concurrent accepted edits can race on `nextVersionNumber`; no runtime race test was present.
10. **P3 — Landing screenshots are not animation-controlled.** The stored comparison supports likely animation timing differences but cannot isolate all shared component or font effects.

## 15. Prioritized remediation recommendations

1. Add an executable What-If acceptance fixture captured from the reported 13/17 movement browser case. Assert target room geometry, every unrelated room's coordinates/dimensions, adjacency/opening diffs, strategy, and persisted/reloaded output for both band and optimizer base plans. Define an explicit product policy when surgery fails (reject or require user approval for a whole-house replan).
2. Add architect review and revise the scorer/functional metrics against reviewed plans, especially 40×60, 80×120 and narrow-deep outputs. Keep geometry validity, functional planning quality, architectural suitability and regulatory compliance as distinct claims.
3. Decide whether ordinary rectangular users should receive the band result, optimizer result or selectable alternatives. Report dimensions and functional metrics, not a lone proxy score; prevent the optimizer from being treated as successful merely because it returns a valid rectangle.
4. Move CPU-bound search to worker threads or a separate optimization service, then define per-user/global admission and cancellation/time budgets. Measure latency and memory under concurrent requests and multiple instances.
5. Re-run production build and browser tests in a writable isolated build directory/runtime; add a real authenticated Supabase integration test for owner, non-owner and guest behavior. Verify accepted 2D and 3D geometry, proposal/accept equality, failure rollback and concurrent version writes.
6. Keep AI integration tests deterministic by mocking provider responses in the default suite; run a separately labeled live-provider evaluation with recorded brief, model, structured output, fallback events and quality rubric.
7. Capture landing screenshots with animation disabled or at controlled animation timestamps and wait for fonts/assets before comparing. Include a harness and diff artifact so shared component changes are covered.

### Severity summary

- **P0:** None confirmed in this audit.
- **P1:** What-If preservation reliability unresolved; ordinary-layout improvements limited; no architect-reviewed quality evidence; synchronous optimizer blocks the server event loop.
- **P2:** Production/browser and authenticated runtime verification gaps; live API dependence in unit suite; non-transactional version-number race risk; AI output quality unmeasured.
- **P3:** Landing screenshot comparison lacks animation control.
